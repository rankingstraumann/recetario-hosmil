# Leads Digital · Outbound (Prospectos) — Arquitectura

Rama: `leads-outbound-v1-preview` (desde `49192dd`, sin merge a main). Estado: **Fase 1 — fundación** (estructura + UI de solo lectura).

## Modelo
```
Planilla / base comercial
  → digital_prospect_imports (lote)  →  digital_prospects (una fila por persona)
  → [futuro] plantilla WhatsApp aprobada, solo si consentimiento = yes y teléfono válido
  → respuesta del prospecto → MISMO bot (Q1–Q5, whatsapp-webhook) → digital_leads (scoring HOT/Tibio/Frío)
  → derivación manual existente.  Al crearse el lead: digital_prospects.linked_lead_id + outreach_status = converted
```
No hay un segundo bot ni un segundo scoring. Los prospectos **no** son leads: no entran a "Nuevos hoy", HOT, Tibios, Fríos, Sin asignar ni Asignados hasta convertirse.

## Tablas (migración `006_outbound_prospectos.sql`)
- `digital_prospect_imports`: filename, source_name, total/imported/skipped/duplicate_rows, created_by, created_at, metadata.
- `digital_prospects`: datos de contacto, `phone_raw` + `phone_e164` (formato `+[1-9]\d{6,14}` o NULL = inválido), `whatsapp_consent` (yes/no/unknown) + `consent_source/at`, `outreach_status` (pending/contacted/replied/opted_out/failed/converted; `eligible` eliminado en 008), `last_outreach_at`, `linked_lead_id → digital_leads` (SET NULL), `is_test`, `raw_payload`, timestamps (trigger `updated_at`).
- Índices no únicos (teléfono, lote, estado, fecha, lead). La política de duplicados se define en la fase del parser.

## Campos comerciales (migración `007`)
`external_customer_id` (Sold-To SAP), `source_owner` (cartera histórica; **no** asigna), `priority_source`, `last_billed_year`, `trade_up_financial`. Lo no mapeado se conserva en `raw_payload`.

## Duplicados (regla para el parser; sin unique sobre teléfono)
1. `external_customer_id` exacto → mismo prospecto (duplicado fuerte). 2. `phone_e164` exacto → posible duplicado, se reporta para revisión. 3. nombre normalizado → solo advertencia, nunca se fusiona automáticamente.

## Elegibilidad (migración `008`): una sola fuente de verdad
- `outreach_status` válidos: `pending, contacted, replied, opted_out, failed, converted` (se eliminó `eligible`: era redundante y podía contradecir al consentimiento/teléfono).
- Columna **generada STORED** `whatsapp_eligible` = `whatsapp_consent='yes'` ∧ `phone_e164` válido ∧ `outreach_status` ∉ {`opted_out`,`converted`}. No se puede escribir a mano ni queda desactualizada. `unknown` y `no` → `false`.
- **Elegible ≠ listo para contactar.** *Listo para contactar* = `whatsapp_eligible = true AND outreach_status = 'pending'`. Un prospecto `contacted`/`replied` sigue siendo elegible pero NO está listo.
- Regla futura del botón "Contactar por WhatsApp": *listo para contactar* (hoy deshabilitado; no hay envío). La UI no recalcula la elegibilidad: lee `whatsapp_eligible`. El parser y el backend de envío deben usar la misma columna.

## Seguridad
- RLS activo en ambas tablas. Única policy: `SELECT` para `authenticated` con `is_lead_admin()` (solo Daniel).
- `authenticated`: solo `SELECT` (sin INSERT/UPDATE/DELETE). `anon`: sin acceso. `service_role`: acceso total (procesos backend futuros).
- No se modificó `digital_leads`, webhook, scoring, secrets, Meta ni cotizaciones.

## UI (admin.html)
Leads Digital → sub-pestañas **[ Leads ] [ Prospectos ]**. Prospectos: contadores (Total, Listos para contactar, Pendientes, Contactados, Respondieron, Convertidos), filtros (búsqueda, origen, consentimiento, estado de contacto, importación, incluir prueba) y tabla. Elegibilidad leída de `whatsapp_eligible`; No / Sin definir / teléfono inválido / baja = no contactar. Botón "Contactar por WhatsApp" **deshabilitado** (no envía nada).

## Outbound 2 — Importador con PREVIEW (no inserta nada)
Prospectos → **⬆ Importar prospectos** → elegir `.xlsx`/`.csv` → Edge Function `prospect-import-preview` → resumen + tabla filtrable. **"Confirmar importación" está deshabilitado**; todo el análisis es de solo lectura (`import_performed:false`).

**Seguridad de la función:** exige sesión y `is_lead_admin()` con el JWT del usuario (sin `service_role`; los duplicados contra BD se leen con RLS del usuario). El archivo se procesa en memoria: no se guarda en Storage ni en la base. Parsing determinista, sin IA ni servicios externos. No se evalúan fórmulas (solo valores). Logs: solo contadores. Límites: 5 MB, 5.000 filas, 20 hojas, 60 columnas, celdas ≤ 2.000 caracteres; extensión y firma (zip/no-zip) validadas.
**Librería:** SheetJS 0.20.3 oficial, build **mini** (solo XLSX) vendorizado en `supabase/functions/prospect-import-preview/vendor/xlsx.mini.mjs` (contenido oficial + una línea `export { XLSX };`; origen, transformación y SHA-256 en `vendor/VENDOR.md`). El CSV NO usa SheetJS: lo procesa `parseCsv`/`decodeCsv`. **Estado de despliegue (2026-10-11):** la función desplegada (v4, `verify_jwt=true`, desplegada desde GitHub Actions) usa esta librería vendorizada; sus 5 archivos son idénticos a los del repo (`xlsx.mini.mjs` SHA-256 `d8471682…f97e`). Ya no hay `npm:xlsx@0.18.5` en producción.

**Mapeo (Trade Up):** Sold-To→`external_customer_id` (texto), Cliente→`clinic_name`, Contacto→`full_name` (vacío = vacío, no se inventa), Cartera original→`source_owner`, Prioridad→`priority_source`, Último año facturado→`last_billed_year`, Trade Up financiero→`trade_up_financial`, Observación→`notes`, el resto (Uso VV, Interés, Próxima acción, Fecha…)→`raw_payload` (todas las columnas originales). `source`='Trade Up', `source_detail`=archivo/hoja, `whatsapp_consent`='unknown', `outreach_status`='pending', `phone_e164`=null si no hay teléfono.

**Validaciones:** Sold-To decimal/científico/caracteres raros → INVÁLIDO; año no entero o fuera de 1990–2100 → INVÁLIDO; fila sin Sold-To/cliente/contacto/teléfono/correo → INVÁLIDO; texto > 300 caracteres → INVÁLIDO; encabezados repetidos dentro de la hoja → excluidos; hojas vacías o sin encabezados reconocibles → informadas y omitidas. Trade Up financiero: `O/SI/SÍ/TRUE/VERDADERO/YES/1`→true, `NO/FALSE/FALSO/0`→false, **vacío→null** (ausencia de marca ≠ "no"), cualquier otro valor→null + advertencia. Teléfonos: celular chileno de 9 dígitos (con/sin 56/+56) → `+569…`; otro formato → sin teléfono + advertencia.
**Duplicados:** Sold-To exacto (archivo o BD) → DUPLICADO (en el archivo queda la primera aparición, las siguientes son duplicados); teléfono exacto → ADVERTENCIA en todos los miembros; nombre normalizado → ADVERTENCIA. Nunca se fusiona.

**Tests:** `supabase/functions/prospect-import-preview/test/` (`make-fixtures.mjs` genera fixtures 100 % ficticios; `run-tests.sh`: 25 casos del análisis + 8 de la confirmación).

## Outbound 3 — Confirmar importación (V1: SOLO datos de prueba)
Flujo: preview válido → **Confirmar importación** (se habilita solo si hay filas listas) → diálogo simple → la UI reenvía **el mismo archivo** con `mode=confirm` a `prospect-import-preview` → la función **re-ejecuta todo el análisis en servidor** (no usa nada del preview del frontend) → llama a la RPC `public.confirm_prospect_import` con el JWT del usuario → resultado «N prospectos importados / N duplicado omitido / N inválidos» → se recarga Prospectos con el filtro **Importación** posicionado en el lote.
- **Qué se inserta:** 1 fila en `digital_prospect_imports` + solo las filas VALIDO/ADVERTENCIA en `digital_prospects`. Duplicado fuerte (Sold-To) → **omitido** (no actualiza ni fusiona; se re-chequea contra la BD dentro de la RPC). Inválidas → no se insertan. Filas sin Sold-To se importan (no pueden ser duplicado fuerte). Advertencias de nombre/teléfono se importan.
- **Valores fijados por la RPC (el cliente no los dicta):** `whatsapp_consent='unknown'`, `outreach_status='pending'`, `is_test=true` (V1), `source='import_excel'`, `phone_e164` NULL si no hay teléfono válido. `raw_payload` conserva las columnas originales (+ `_sheet`, `_row`). Códigos siempre como texto.
- **Seguridad:** RPC `SECURITY DEFINER` (`search_path=pg_catalog`) que exige `is_lead_admin()`; `EXECUTE` solo a `authenticated` (no `anon`/`public`). **No se abrió INSERT directo** a ninguna tabla. Sin `service_role`. Logs: solo contadores.
- **Atómica:** toda la importación ocurre dentro de una sola llamada/transacción; si algo falla (p. ej. teléfono con formato inválido en una fila) no queda nada. **Doble confirmación:** `file_sha256` (SHA-256 del archivo) con índice único + `pg_advisory_xact_lock` → un mismo archivo no puede confirmarse dos veces (409 «ya fue importado»); en la UI el botón queda deshabilitado tras importar.
- **Conteos registrados** en el lote: `total_rows`, `imported_rows`, `duplicate_rows`, `skipped_rows` (= inválidas); `metadata.is_test=true`. Invariante validada en servidor y en la RPC: importadas + inválidas + duplicados = total.
- **Migración:** `sql/leads-digital/009_outbound_confirmar_importacion.sql` (rollback `999f_…`; no borra datos importados).
- **Despliegue:** requiere publicar la versión nueva de la Edge Function (ver estado de despliegue arriba); hasta entonces la UI mostrará error al confirmar.

## Outbound 4 — Importación REAL controlada (migración 010)
El mismo flujo (archivo → preview → confirmar) con un selector **Modo del lote: PRUEBA / REAL** (solo Lead Admin; **PRUEBA por defecto**, se restablece al abrir/cerrar el panel o descartar). Al elegir REAL: aviso rojo «Este lote se incorporará como prospectos comerciales reales.», el preview se recalcula en ese modo y confirmar exige **doble confirmación**: diálogo + escribir exactamente `IMPORTAR REAL`.
- **El servidor decide `is_test`:** la Edge Function valida `batch_mode` (`test`|`real`; cualquier otro valor se rechaza, nunca cae a REAL) y REAL exige `real_confirmed='yes'` al confirmar; la RPC `confirm_prospect_import` recibe `p_is_test` + `p_real_confirmed` y rechaza REAL sin confirmación (`CONFIRMACION_REAL_REQUERIDA`). `PRUEBA → is_test=true`, `REAL → is_test=false`, tanto en el lote como en cada prospecto.
- **Sin cambios para lotes reales:** `whatsapp_consent='unknown'`, `outreach_status='pending'`, sin contacto automático ni WhatsApp outbound, duplicados fuertes omitidos, inválidos no insertados, operación atómica.
- **Columna nueva:** `digital_prospect_imports.is_test` (modo del lote; backfill desde `metadata.is_test`, lotes previos = PRUEBA). Filtro «Importación»: `[PRUEBA] archivo` / `[REAL] archivo`.
- **Regla de doble importación (decisión):** unicidad por **(`file_sha256`, `is_test`)**. El mismo archivo no se puede importar dos veces *en el mismo modo*, pero una importación de PRUEBA **no bloquea** la importación REAL del mismo archivo (ni al revés). Alternativa descartada: unicidad solo por hash, que dejaría a un ensayo con el archivo real bloqueando para siempre su importación real.
- **Regla de duplicados contra la base (decisión):** el Sold-To duplicado se busca **solo dentro del mismo modo** (`is_test` igual), tanto en el preview como dentro de la RPC. Así los prospectos de prueba no convierten en «duplicado» a un prospecto real, y un lote real no queda contaminado por ensayos. Duplicados dentro del propio archivo se tratan igual que antes.
- **Se elimina la firma anterior de la RPC** (7 args) para que no exista una vía de escritura sin modo explícito. Rollback: `999g_rollback_outbound_importacion_real.sql`.
- **Despliegue:** la migración 010 y la Edge Function se publican juntas (la función antigua llamaba a la firma eliminada). Aplicadas y validadas el 2026-10-11: pruebas de BD en transacción revertida (hash por modo, duplicados por modo, REAL exige confirmación, `anon` sin permiso, firma de 7 argumentos inexistente).

## Outbound 5 — Enriquecer prospectos REALES (migración 011)
Botón **✚ Enriquecer prospectos** dentro de Prospectos (excluyente con el panel de importación). Flujo: archivo mínimo (.xlsx/.csv con `Sold-To` + `Contacto`/`Teléfono`/`Email`) → **preview** → revisar → **confirmar**. Solo Lead Admin. El archivo se procesa en memoria y no se guarda.
- **Match:** únicamente por `external_customer_id` = Sold-To **exacto** (texto; `1234567` ≠ `0001234567`) contra prospectos `is_test=false`. Sin match → se informa y no se hace nada: **nunca se crea un prospecto**. Sold-To repetido en el archivo o en la base → excluido (no se adivina).
- **Campos permitidos:** `full_name`, `phone_raw`+`phone_e164` (juntos, solo móvil válido +569XXXXXXXX), `email` (minúsculas, formato válido). **Solo se llena lo vacío**: un dato existente distinto es «conflicto» y se conserva; un valor vacío del archivo nunca pisa ni borra nada.
- **Intocables:** `whatsapp_consent`, `consent_*`, `outreach_status` y cualquier otra columna; no se envía WhatsApp. La RPC solo escribe esas 3 columnas (un test verifica que consentimiento/estado/elegibilidad quedan idénticos).
- **Preview:** filas del archivo, match exacto, sin match, con móvil válido, sin móvil, teléfonos duplicados (dentro del archivo o contra otro prospecto de la base), contactos / móviles / emails a completar, conflictos, inválidas, repetidas. La tabla muestra Sold-To, qué se completa y advertencias, **sin nombres, teléfonos ni correos**.
- **Teléfonos duplicados:** se advierten antes de confirmar; el botón queda deshabilitado hasta marcar «Revisé los teléfonos duplicados» y el servidor lo exige (`dup_ack=yes`). No se bloquea la carga (un mismo teléfono puede ser legítimo).
- **Confirmación atómica:** Edge Function (`mode=enrich_preview|enrich_confirm`) re-analiza el archivo en servidor con la sesión del usuario (sin `service_role`) y llama a la RPC `confirm_prospect_enrichment`. La RPC (SECURITY DEFINER, EXECUTE solo `authenticated`) revalida todo: Lead Admin, forma de cada elemento (solo claves permitidas), prospecto existente + `is_test=false` + Sold-To idéntico (con `FOR UPDATE`), campo aún vacío; si un solo prospecto no calza **aborta todo**. Anti doble aplicación por `file_sha256` único.
- **Auditoría / rollback dirigido:** `digital_prospect_enrichments` (1 fila por archivo, conteos) y `digital_prospect_enrichment_items` (ids de prospecto + nombres de campo llenados; sin datos personales). Como solo se llenan campos vacíos, el estado previo era NULL: ver el `UPDATE` de ejemplo en `999h_rollback_outbound_enriquecimiento.sql`.
- **Logs:** solo contadores y códigos (sin nombres/teléfonos/correos/filas).
- **Despliegue:** migración 011 aplicada (sin DROP) el 2026-10-11 y validada con 19 pruebas de BD en transacción revertida con datos ficticios. La Edge Function necesita **redeploy** (GitHub Actions) para exponer los modos `enrich_*`; hasta entonces el botón fallaría con «Modo no válido». **Los 138 prospectos reales NO han sido modificados.**

## Outbound 6 — Control de consentimiento WhatsApp (migración 012)
Gestión **individual, con evidencia y auditada** del consentimiento. Solo Lead Admin. No envía WhatsApp, no crea plantillas, no cambia `outreach_status`.
- **Estados:** Sin definir (`unknown`) / Autorizado (`granted`) / No autorizado (`denied`). *Almacenamiento:* se conservan los valores previos de `whatsapp_consent` (`unknown`/`yes`/`no`) porque la columna generada `whatsapp_eligible` y los CHECK dependen de ellos; `yes`=granted, `no`=denied. La RPC, la auditoría y la UI hablan en granted/denied/unknown.
- **Nunca automático:** tener teléfono no autoriza nada; el import y el enriquecimiento siguen dejando `unknown`.
- **RPC `set_prospect_consent(prospect, estado, fuente, fecha, nota)`** (SECURITY DEFINER, EXECUTE solo `authenticated`, `is_lead_admin()` adentro, **un prospecto por llamada → no existe actualización masiva**). *granted* exige fuente (lista cerrada: formulario web, correo, opt-in WhatsApp, llamada registrada, presencial, evento, otro), fecha (no futura, ≥2015), nota ≥5 caracteres. *denied*: fecha (defecto hoy), fuente y motivo opcionales. *Volver a Sin definir*: motivo obligatorio, limpia fuente/fecha. Rechaza mismo estado (`SIN_CAMBIO`) y autorizar a un prospecto dado de baja (`opted_out`).
- **Auditoría `digital_prospect_consent_log`:** prospect_id, estado anterior/nuevo, fuente, fecha del consentimiento, nota, `changed_by` (+ email), `changed_at`. SELECT solo Lead Admin; sin escritura directa.
- **Guardia en la base (`trg_guard_prospect_consent`):** `whatsapp_consent`, `consent_source` y `consent_at` solo pueden cambiar si existe una fila de auditoría **de la misma transacción, aún no aplicada, con ese estado**; cada fila autoriza exactamente un cambio. Bloquea UPDATE masivo/manual (incluso como propietario) e INSERT con consentimiento ≠ unknown. Las demás columnas (p. ej. enriquecimiento) siguen editables.
- **«Listo para contactar» = columna generada `contact_ready`:** prospecto REAL (`is_test=false`) + `phone_e164` `+569XXXXXXXX` + consentimiento granted + `outreach_status='pending'`. Única definición; la UI no la recalcula (`whatsapp_eligible` se mantiene aparte).
- **UI (Prospectos):** filtro Sin definir / Autorizado / No autorizado; acción por fila «Registrar consentimiento» (panel con estado, fuente, fecha, nota, confirmación e historial); fuente y fecha visibles; contador «Listos para contactar» y resumen autorizados/no autorizados/sin definir. Sin `service_role`: `sb.rpc` con la sesión del usuario. El botón «Contactar por WhatsApp» sigue deshabilitado.
- **Despliegue:** solo migración 012 + `admin.html`; **la Edge Function no cambia (sin redeploy)**. Rollback: `999i_rollback_outbound_consentimiento.sql` (no revierte datos; respaldar el log antes si ya hay registros).
- **Validación:** 36 pruebas de BD en transacciones revertidas con datos ficticios y 30 comprobaciones de UI; los 138 reales siguen `unknown`, sin fuente ni fecha, `pending`.

## Outbound 6B — Captura digital de consentimiento por link individual (migración 013)
Flujo: Lead Admin genera invitación → el cliente abre `consentimiento-whatsapp.html?t=<token>` → autoriza o rechaza → queda registrado en la auditoría de Outbound 6. **No envía email ni WhatsApp, no crea plantillas, no cambia `outreach_status`, no crea prospectos.**
- **Token:** 32 bytes de `gen_random_bytes` (CSPRNG), base64url de 43 caracteres. Se muestra **una sola vez** al Lead Admin (respuesta de `create_consent_invitation`, solo en memoria de la UI); la base guarda **solo el SHA-256**. No contiene Sold-To, email, teléfono ni UUID. Un solo uso (`pending → accepted|rejected`) y vencimiento (14 días por defecto, 1–60).
- **Tabla `digital_prospect_consent_invitations`:** prospecto, `token_hash` único, estado (`pending/accepted/rejected/revoked`), creada por, creada/vence/usada, decisión, vínculo a la fila de auditoría y `evidence` (jsonb). El Lead Admin lee estado y fechas por columnas permitidas; **nunca `token_hash` ni `evidence`** vía API (la evidencia se consulta con SQL de administración). «Vencida» se deriva (`pending` con `expires_at` pasado); un token vencido **no se modifica**.
- **RPC de Lead Admin:** `create_consent_invitation(prospecto, ttl)` (solo prospectos «Sin definir» y no `opted_out`; revoca el link vigente anterior) y `revoke_consent_invitation`. `anon` no puede ejecutarlas.
- **RPC públicas (anon) solo con token válido:** `get_consent_invitation(token)` → `{valid}` y `submit_consent_invitation(token, decisión, casilla)` → `{ok}`. Respuesta **neutra**: no distingue token inválido / usado / vencido / revocado ni revela datos. `anon` no tiene permisos sobre ninguna tabla (verificado: no lee prospectos, invitaciones ni auditoría). Opera **solo sobre el prospecto asociado al token**.
- **Aceptar** exige casilla marcada y registra `granted`, `source=formulario_web`, fecha actual (America/Santiago), `consent_at=now()`, auditoría en `digital_prospect_consent_log` (`changed_by` nulo, «cliente (formulario web)») y evidencia automática: versión del texto (`consent_wa_v1`) y su SHA-256, casilla, decisión, IP y user-agent de las cabeceras. **Rechazar** registra `denied` con el mismo historial. Si el prospecto ya tenía ese estado, se consume el token sin duplicar auditoría. `opted_out` no puede autorizar (puede rechazar).
- **Página pública:** HTML estático sin librerías ni storage, casilla no premarcada, botón «Autorizar WhatsApp» deshabilitado hasta marcarla y «No deseo recibir mensajes por WhatsApp»; texto idéntico al que la RPC hashea (test). `noindex`, `no-referrer`, CSP restringida a Supabase y cabeceras en `vercel.json` (`no-store`, `X-Frame-Options: DENY`). Sin `console.*` (sin PII en logs).
- **UI Lead Admin (panel «Registrar consentimiento»):** «Generar link de consentimiento» (con confirmación), «Copiar link», lista de invitaciones con estado (pendiente / aceptada / rechazada / vencida / revocada), fecha de creación y vencimiento, «Revocar»; resumen del estado en la celda de consentimiento. El token no se vuelve a mostrar al cerrar el panel.
- **Despliegue:** migración 013 + `consentimiento-whatsapp.html` + `vercel.json` + `admin.html`; **la Edge Function no cambia**. Rollback: `999j_rollback_outbound_consentimiento_digital.sql` (no revierte consentimientos ya registrados).
- **Límites conocidos:** sin rate-limit específico en las RPC públicas (el token de 256 bits hace inviable adivinarlo); si se pierde el link hay que generar otro; no hay envío del link (se copia y se envía a mano).

## Outbound 7 — Contacto inicial por plantilla WhatsApp, SOLO MODO PRUEBA (migración 014)
**Nada se envía a prospectos reales.** Un prospecto por acción, sin reintentos automáticos, solo Lead Admin.
- **Arquitectura:** `admin.html` (botón «Enviar plantilla de prueba» → modal) → Edge Function `outbound-whatsapp-send` (JWT del usuario + `is_lead_admin()`, sin `service_role`) → RPC `claim_outbound_send` (reserva atómica) → Meta (plantilla) → RPC `finalize_outbound_send`. Lógica pura en `logic.ts` (probada sin red).
- **Barreras en orden (todas ANTES de reservar/enviar):** (1) kill switch `OUTBOUND_WHATSAPP_ENABLED` (**apagado por defecto**; solo `'true'` lo enciende); (2) `OUTBOUND_WHATSAPP_TEST_ONLY` (defecto `true`; con `false` la función **rechaza** — el modo real no existe en esta versión); (3) plantilla configurada (`OUTBOUND_TEMPLATE_NAME` + `OUTBOUND_TEMPLATE_LANGUAGE`, validados; **no se crea ninguna plantilla en Meta**); (4) la RPC valida en la base: `is_test=true` (**un REAL se rechaza server-side aunque el frontend lo pida; el cliente solo envía `{action, prospect_id}`**), consentimiento `yes`, móvil `+569XXXXXXXX`, `outreach_status='pending'`.
- **Modo real vs simulación:** envío real solo si `OUTBOUND_TEMPLATE_APPROVED='true'` **y** existen `WHATSAPP_ACCESS_TOKEN` + `WHATSAPP_PHONE_NUMBER_ID` (secretos que ya usa el webhook inbound). Si falta algo → **simulación (dry-run)**: no llama a Meta, registra `dry_run`, el prospecto sigue Pendiente. El modal lo avisa («modo SIMULACIÓN»).
- **Idempotencia:** `digital_outbound_sends` con índice único parcial (1 envío `sending`/`sent` por prospecto) + `FOR UPDATE` en la reserva ⇒ doble clic = un solo envío (el otro recibe `ENVIO_EN_CURSO`); tras éxito el prospecto ya no es `pending`. Si el registro final falla, la fila queda `sending` (bloquea otro envío; se resuelve manualmente — nunca se reintenta solo).
- **Registro (`digital_outbound_sends`):** prospect_id, template_name/language, status (`sending/sent/failed/dry_run`), provider_message_id, error_code, error_message **sanitizado** (sin teléfonos/tokens, ≤200), requested_by(+email), requested_at, completed_at, sent_at.
